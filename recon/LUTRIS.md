# 第一阶段：官方客户端的 Lutris 运行适配

日期：2026-11-14。官方游戏 1.0.2 / build 12450 / bilibili。升级 DXVK 后已观察到剧情角色、场景与对白正常显示；用户确认已经能玩，并判断此前移动异常来自教程锁定操作。核显场景帧率约 10 FPS，用户选择暂不继续优化，当前配置作为第一版可玩基线保留。

## 范围与验收

第一阶段复用官方游戏本体，通过 Lutris 管理兼容环境。后续原生重写范围聚焦启动器：安装、官方版本发现、下载更新、校验、环境与进程管理，以及确有必要的登录适配。游戏自己的心跳、重连、场景、渲染和玩法保持官方实现。

用户已确认当前配置能玩。登录与进入场景已有实际游戏证据；跳跃、闪避未逐项单独记录，因此不把“可玩”扩大为全部玩法和稳定性测试通过。启动画面可见或独立网关实验成功均不足以通过可玩性验收。

## 黑屏调查

初始基线使用 Wine 11.21 + DXVK 2.6.2。启动与资源加载画面正常，进入游戏后出现全黑画面，仍显示 FPS 与 UID。日志在开始播放 MP4 后持续报告：

```text
Got null handle from IDXGIResource::GetSharedHandle.
```

保留的修改前日志累计 248 条该错误，支持优先检查视频共享纹理路径；此处不把它泛化为所有黑屏的唯一原因。

[DXVK 3.0 官方说明](https://github.com/doitsujin/dxvk/releases/tag/v3.0)新增了普通 Wine 的共享资源支持。下一轮只把 DXVK 改为 3.0.2，其余配置保持不变，通过 Lutris 自身的版本管理链接 DLL，不改游戏资源或业务程序集。

下载来源：[官方 3.0.2 发布页](https://github.com/doitsujin/dxvk/releases/tag/v3.0.2)。压缩包 SHA-256 已与 GitHub release asset digest 核对：

```text
9c538924110a7cdef871ca36dee218c0774124374ffdeb38af4b76be55bdf7c2
```

已确认 3.0.2 的 DLL 链接与进程内加载生效。重新登录进入游戏后，窗口已显示剧情角色、场景和对白，本轮截至该观察点的共享句柄错误为 0；此前全黑状态已恢复显示。脱敏比较见 [lutris-compatibility.json](verification/lutris-compatibility.json)。这项结果不代表所有后续视频、场景和操作均已验证。

更新 DXVK 后首次启动重新预热了着色器，加载期间的低帧率不能作为场景性能结论。游戏自身设置把请求的 1280×720 覆盖成了 1920×1080；后续需要在游戏设置中确认实际分辨率和画质，再比较性能。

## 性能比较：已按用户要求结束

当前窗口实测为 1920×1080，用户报告场景内约 10 FPS。对游戏进程的 DRM fdinfo 计数器做约 3 秒采样，省电模式下 render 引擎忙碌率约 99.3%；采样时可用内存约 13 GiB。该样本支持优先检查 GPU 渲染负担，不据此量化 Wine 相对 Windows 的性能损失。

发现系统原本处于 `power-saver`。用户选择第一轮只临时改为 `balanced`，保持分辨率、画质与运行器不变比较。用户反馈表现差不多，并明确选择不再纠结性能；未获得足以量化收益的配对 FPS 数据，不宣称有性能提升。

本轮曾由临时用户级 systemd 服务负责恢复电源模式：若仍为测试用的均衡模式则恢复省电，若模式已被其他操作改变则保留。用户结束性能测试后已停止该服务；停止时系统已是 `performance`，恢复逻辑按约定保留了这一外部变化，游戏继续运行。临时均衡模式没有写入 Lutris 的默认启动配置。

本轮没有继续修改分辨率或画质。若将来重新开展性能优化，可优先比较 1280×720 与低画质；当前保留已经解决黑屏的 Wine 11.21 + DXVK 3.0.2 组合。
